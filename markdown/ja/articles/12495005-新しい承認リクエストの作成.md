# 新しい承認リクエストの作成

新しい承認リクエストアクションは、2025年10月2日以降に共有リビジョンを有効にしたプロジェクトで確認できます。[承認ページ](https://support.catenda.com/en/articles/8349340-approvals-page)の緑色のプラスボタンの右側にあるアクションメニューをクリックして、新しい承認リクエストを作成します。ドキュメントページの右メニューの承認メニューで、最新のリビジョンが共有リビジョンであるリビジョンの右メニューの新しい承認リクエストボタンをクリックして、新しい承認リクエストを作成します。これが新しい承認リクエストダイアログのようなものです:

![新しい承認リクエスト Workflow Submitter Title Description (optional) ドキュメント レビュー ドキュメント追加 name revision # Revision number ステータス Remove Cancel Save as draft Submit for review](https://raw.githubusercontent.com/catenda/help-center/main/images/4e7kgq0a/01-intro.png)

2025年10月2日以前に共有リビジョンを有効にしたプロジェクトは、代わりにレガシーの新しい承認リクエストダイアログが表示されます。

## 1. 承認リクエストヘッダー

これは、2025年10月2日以降に共有リビジョンを有効にしたプロジェクトの新しい承認のヘッダーのようなものです:

![新しい承認リクエスト Workflow Submitter Title](https://raw.githubusercontent.com/catenda/help-center/main/images/4e7kgq0a/02-approval-request-header.png)

### 1.1 **ワークフロー選択**

プロジェクトワークフローで構成された送信チームの一部であるメンバーは、そのチームが構成されているワークフローの1つから選択できます。以前に選択されたワークフローは記憶されます。以前に選択されたワークフローがまだ利用可能である限り、次回承認が作成されるときに再度選択されます。

**自動選択**メンバーが属するチームの1つだけがワークフロー用に構成されている場合、そのワークフローは自動的に選択されます。これは、ワークフローが自動的に選択されるときのような外観です。

![Workflow Submitter Title](https://raw.githubusercontent.com/catenda/help-center/main/images/4e7kgq0a/03-workflow-selection.png)

_必要なアクセス:_ メンバーと管理者は、ワークフローを選択できるようにワークフロー用に構成された送信チームの一部である必要があります。

### 1.2 **送信者選択**

ワークフローが選択された後、ワークフロー用に構成された複数の送信チームの一部であるメンバーは、どのチームの代わりに承認リクエストを送信したいかを選択できます。以前に選択された送信チームは記憶されます。メンバーが以前に選択された送信チームの一部である限り、次回承認が作成されるときに再度選択されます。

承認リクエストが作成されると、選択された送信チームの一部であるメンバーはリクエストが表示されますが、他の可能な送信チームの一部であるメンバーは、レビュアーチームの1つの一部であるか、ワークフロー用に構成された最終承認チームの一部である場合にのみリクエストが表示されます。

**自動選択**メンバーがワークフロー用に構成された送信チームの1つだけの一部である場合、ワークフローが選択されると、送信チームが自動的に選択されます。

![Workflow Submitter Title](https://raw.githubusercontent.com/catenda/help-center/main/images/4e7kgq0a/04-submitter-selection.png)

_必要なアクセス:_ メンバーと管理者は、その送信チームの代わりに送信できるようにワークフロー用に構成された送信チームの一部である必要があります。

### 1.3 **タイトル**

承認リクエストのタイトル。承認には、送信するためのタイトルが必要です。

## 2. **承認リクエストボディ**

新しい検証ワークフローは、新しいプロジェクトを開始するときに有効にするようにリクエストできるオンデマンド機能です。新しい検証ワークフローがテンプレートプロジェクトで有効になっていない場合、テンプレートプロジェクトに基づいてプロジェクトを作成することのみが可能です。これが、2025年10月2日以降に共有リビジョンを有効にしたプロジェクトの新しい承認のボディのようなものです:

![承認リクエスト本文 Description (optional) ドキュメント レビュー ドキュメント追加 cancel no documents added yet](https://raw.githubusercontent.com/catenda/help-center/main/images/4e7kgq0a/05-approval-request-body.png)

### 2.1 **説明**

承認の説明は、[投稿の一般的な書式ルール](https://support.catenda.com/en/articles/8430847-formatting-of-posts)に従います。

### 2.2 **ドキュメントの追加**

![Description (optional) ドキュメント レビュー ドキュメント追加](https://raw.githubusercontent.com/catenda/help-center/main/images/4e7kgq0a/06-add-documents.png)

[ここ](https://support.catenda.com/en/articles/12382093-add-revision-to-approval)をクリックして、ドキュメントから承認リクエストに共有リビジョンを追加する方法の詳細をご覧ください。ここに無限の量のドキュメントを追加することは可能ですが、レビュー用に承認リクエストを送信する制限は1000ドキュメントです。

### 2.3 **レビューテーブル用ドキュメント**

これは、検証対象の各ドキュメント内の共有リビジョンが追加された後のレビューテーブル用ドキュメントのようなものです:

![ドキュメント レビュー テーブル Name revision # Revision number ステータス Remove Cancel Save as draft Submit for review](https://raw.githubusercontent.com/catenda/help-center/main/images/4e7kgq0a/07-documents-for-review-table.png)

**列**構成された列の順序に基づいて、最初の列が表示される一方、テーブルを横方向にスクロールして、有効な他の列を表示する必要があります。ドキュメントページの列のデフォルト順序と表示設定は次のとおりです:

_名前_ - _デフォルト_ 共有リビジョンが存在するドキュメントの名前。ドキュメント名はドキュメント内のすべてのリビジョンで同じです。

リビジョン - _デフォルト_ ドキュメントリビジョンの名前。これはアップロードされたファイルの元のファイル名と同じです。

## 3. - _デフォルト_

ステータス - _デフォルト_ 共有リビジョンに適用された共有ステータスの名前。

削除 - _デフォルト_ 削除列のxをクリックして、レビュー対象のドキュメントをドキュメントレビューリストから削除します。

## 4. **下書きとして保存**

承認リクエストを送信およびロックする前に編集します。

### 4.1 **下書きに1000を超えるドキュメント**

承認リクエストダイアログに多数のドキュメントを追加することは可能ですが、最大1000ドキュメントのrevisionでダイアログを送信することのみ可能です。新しい検証ワークフローで1000を超えるドキュメントrevisionを追加するには、まず最大1000ドキュメントを追加し、承認リクエストを下書きとして保存します。次に、承認リクエストを送信する前に、下書き承認リクエストページの[ドキュメントを追加]操作で一度に最大1000ドキュメントを下書きに追加します。

### 4.2 **準備ができたら1段階目のレビュー期間を開始**

承認リクエストが送信されると同時に、選択された承認ワークフローの最初の段階に設定されたレビュアーチームは、承認リクエストのrevisionをレビューするタスクが割り当てられます。レビュアーチームのメンバーは、承認ステップに設定されている営業日が終了するまでrevisionをレビューできます。承認リクエストを下書きとして保存すると、ワークフローの準備ができたら即座に送信できます。

承認リクエストワークフローを送信して、選択されたワークフローに設定されたレビュアーチームの最初のステップのレビュー期間を開始する前に、レビューステップが開始されようとしていることを伝えることで、チームの準備が整っていることを確認してください。

ワークフロー内の営業日の合計数をワークフローが送信される日数に合わせることで、ワークフローの最終公開日が適切な時刻に終了するようにしてください。

## 5. **レビューのために送信**

[レビューのために送信]をクリックして承認を送信し、承認プロセスを開始します。レビューのために承認リクエストを送信するには、以下が必要です。

- 承認リクエストが従うワークフローを選択する必要があります。
- 代理で送信するサブミッターチームを選択する必要があります
- タイトル
- ドキュメント
  - 承認を送信するには、選択された共有revisionを持つ最小1つのドキュメントを追加する必要があります。
  - 選択された共有revisionを持つ最大1000ドキュメントrevisionを追加できます。
  - 1000を超えるドキュメントrevisionで承認リクエストを作成するには、まず最大1000revisionで下書きを作成してから、送信する前に一度に最大1000ドキュメントrevisionを下書きに追加してレビューのために下書きを送信します。

新しい検証ワークフローで承認リクエストをレビュー用に送信した後、変更可能な唯一のことは、共有revisionドキュメントをリクエストから破棄できることです。

_準備ができたら1段階目のレビュー期間を開始_ 承認リクエストが送信されると同時に、承認ワークフローに設定された最初のレビューステップの期間が開始されます。
